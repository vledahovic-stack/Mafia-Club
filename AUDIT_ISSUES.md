### 1. `PERF-01`: Отсутствие очистки неактивных комнат и накопление неуничтожаемых таймеров
* **Уровень критичности:** **P1 (Высокий)**
* **Подсистема:** Игровой движок / Управление памятью
* **Статус:** Подтверждено
* **Конкретные файлы и функции:**
  * Файл: `server/game/roomManager.ts`
  * Класс/методы: `Room.constructor`, `Room.startHeartbeatTimer()`, `RoomManager.removeRoom()`
* **Техническое доказательство проблемы:**
  В строках 158–165 конструктора класса `Room` при создании каждой комнаты создаётся постоянный таймер:
  ```typescript
  this.timerInterval = setInterval(() => {
    this.tick();
  }, 1000);
  ```
  Метод `removeRoom(roomCode)` в кодовой базе вызывается исключительно в одном месте — администратором вручную через эндпоинт `POST /api/admin/rooms/close` (`server.ts`, строка 2226). При отключении всех игроков комната лишь переводит участников в `player.connected = false`, но комната не удаляется из карты `RoomManager.rooms`, и таймер продолжает тикать каждую секунду бесконечно.
* **Условия возникновения:** Естественный жизненный цикл приложения — игроки создают публичные или приватные комнаты, доигрывают или покидают их.
* **Возможные последствия:** Утечка памяти (удержание сокетов, сообщений чата и снимков состояния) и постепенная деградация CPU сервера из-за сотен параллельно работающих холостых таймеров `setInterval`.
* **Рекомендуемый способ исправления:**
  Внедрить в `RoomManager` фоновый интервал (раз в 60 секунд) для очистки комнат («Garbage Collector»): если в комнате фаза `LOBBY` или `GAME_OVER` и в течение 10–15 минут нет ни одного подключённого игрока (`sockets.size === 0` или `players.every(p => !p.connected)`), вызывать `this.removeRoom(code)`.
* **Необходимые проверки после исправления:** Проверить создание комнаты, отключение всех игроков, ожидание таймаута и корректное освобождение ресурсов с вызовом `room.destroy()`.

### 2. `INFRA-01`: Эфемерность локальной базы SQLite при развёртывании на Render Free Tier
* **Уровень критичности:** **P1 (Высокий)**
* **Подсистема:** Инфраструктура развёртывания / Сохранность данных
* **Статус:** Подтверждено
* **Конкретные файлы и функции:**
  * Файлы: `server/db/database.ts` (`initDatabase`, `getDatabaseConnectionInfo`), `server.ts` (строки 40–50), `.env.example`
* **Техническое доказательство проблемы:**
  Функция `initDatabase()` считывает переменные `TURSO_DATABASE_URL` и `TURSO_AUTH_TOKEN`. Если они не заданы, сервер инициализирует локальный файл:
  ```typescript
  const url = rawTursoUrl || `file:${SQLITE_DB_PATH}`;
  ```
  На хостинге Render (тариф Free) контейнеры запускаются с эфемерной файловой системой (ephemeral storage). Любой перезапуск сервера, деплой новой версии или переход контейнера в спящий режим полностью стирает файл `database.sqlite`, сбрасывая всех пользователей, инвентарь и матчи к начальному сиду.
* **Условия возникновения:** Развёртывание проекта на Render без предварительного создания базы данных в Turso и без прокидывания `TURSO_DATABASE_URL`.
* **Возможные последствия:** Полная потеря базы данных игроков, наград, истории покупок и кланов при первом же перезапуске контейнера на Render.
* **Рекомендуемый способ исправления:**
  1. Перед публичным релизом обязательно зарегистрировать production-базу в сервисе Turso Cloud.
  2. В панели управления Render в Environment Variables жестко зафиксировать `TURSO_DATABASE_URL` и `TURSO_AUTH_TOKEN`.
  3. В `server.ts` добавить блокировку старта в production (`process.env.NODE_ENV === 'production' && !process.env.TURSO_DATABASE_URL`), чтобы предотвратить случайный запуск на эфемерном диске с реальными игроками.
* **Необходимые проверки после исправления:** Перезапуск контейнера на Render и проверка сохранения созданной тестовой учетной записи.

### 3. `COSM-01`: Отсутствие сохранения экипированного скина интерфейса (`uiSkin`) в базе данных
* **Уровень критичности:** **P2 (Средний)**
* **Подсистема:** Косметика и инвентарь / Профиль пользователя
* **Статус:** Подтверждено
* **Конкретные файлы и функции:**
  * Файлы: `server/db/users.ts` (`equipSkin`, строки 1988–2018; `rowToUser`, строки 221–224), `server/db/database.ts` (схема таблицы `users`)
* **Техническое доказательство проблемы:**
  В таблице `users` присутствуют колонки `equipped_card_back` и `equipped_title`, но отсутствует колонка для скина темы интерфейса.
  В методе `equipSkin` сервер проверяет владение предметом и выполняет:
  ```typescript
  user.equippedCosmetics = user.equippedCosmetics || {};
  user.equippedCosmetics.uiSkin = skinId;
  await this.db.execute({
    sql: 'UPDATE users SET updated_at = ? WHERE id = ?',
    args: [new Date().toISOString(), userId],
  });
  ```
  Значение `skinId` не записывается ни в какую колонку SQL! Метод `rowToUser` при чтении из базы восстанавливает только `cardBack` и `title`:
  ```typescript
  equippedCosmetics: {
    cardBack: row.equipped_card_back || undefined,
    title: row.equipped_title || undefined
  }
  ```
* **Условия возникновения:** Игрок покупает скин интерфейса на Черном Рынке и нажимает «Экипировать».
* **Возможные последствия:** При следующей перезагрузке страницы или при запросе `getUserById` скин сбрасывается в `default`.
* **Рекомендуемый способ исправления:**
  1. Добавить миграцию в `database.ts`: `ALTER TABLE users ADD COLUMN equipped_ui_skin TEXT;`.
  2. Обновить `rowToUser`: `uiSkin: row.equipped_ui_skin || undefined`.
  3. В `equipSkin` выполнять запись: `UPDATE users SET equipped_ui_skin = ?, updated_at = ? WHERE id = ?`.
* **Необходимые проверки после исправления:** Экипировка скина, перезагрузка страницы, проверка сохранения в `user.equippedCosmetics.uiSkin`.

### 4. `ECON-01`: Повторное начисление кредитов при повторном сохранении резолюции обращения (`feedbacks`)
* **Уровень критичности:** **P2 (Средний)**
* **Подсистема:** Административная панель / Обратная связь
* **Статус:** Подтверждено
* **Конкретные файлы и функции:**
  * Файл: `server.ts`
  * Эндпоинт: `POST /api/admin/feedbacks/resolve` (строки 3316–3345)
* **Техническое доказательство проблемы:**
  При обработке тикета администратором:
  ```typescript
  const rewardAmount = typeof rewardCredits === 'number' && rewardCredits > 0 ? Math.floor(rewardCredits) : 0;
  if (rewardAmount > 0) {
    try {
      targetUserUpdated = await userDb.adminUpdateCredits(current.userId, rewardAmount, false);
    } catch (userErr) {}
  }
  ```
  Сервер начисляет кредиты пользователю без проверки того, были ли кредиты уже начислены за это обращение ранее (`current.rewardCredits > 0`).
* **Условия возникновения:** Администратор сначала одобрил баг-репорт с наградой 100 кредитов (статус `reviewed`), а затем изменил статус на `fixed` или отредактировал административную заметку, оставив в поле награды 100.
* **Возможные последствия:** Повторное несанкционированное начисление кредитов на баланс пользователя (дублирование выплаты).
* **Рекомендуемый способ исправления:**
  Начислять кредиты только в том случае, если ранее награда не выдавалась (`!current.rewardCredits || current.rewardCredits === 0`), либо начислять только положительную разницу `rewardAmount - (current.rewardCredits || 0)`.
* **Необходимые проверки после исправления:** Создать обращение, начислить 50 кредитов, затем повторно сохранить с 50 кредитами — убедиться, что баланс пользователя увеличился ровно один раз.

### 5. `GAME-02`: Зависание комнаты в лобби при выходе ведущего (Host Disconnect)
* **Уровень критичности:** **P2 (Средний)**
* **Подсистема:** Игровой движок / Управление комнатами
* **Статус:** Подтверждено
* **Конкретные файлы и функции:**
  * Файлы: `server.ts` (`ws.on('close')`, строки 5140–5166), `server/game/roomManager.ts` (`removePlayer`, строки 1082–1085)
* **Техническое доказательство проблемы:**
  В методе `removePlayer` смена хоста реализована корректно:
  ```typescript
  if (player.isHost && this.state.players.length > 0) {
    this.state.players[0].isHost = true;
  }
  ```
  Однако при обычном закрытии браузера хостом срабатывает только обработчик `ws.on('close')`, который вызывает лишь `player.connected = false`, не вызывая `removePlayer`. В результате комната остаётся с отключённым хостом, а оставшиеся активные игроки не имеют кнопки «Начать игру» или «Добавить бота».
* **Условия возникновения:** Ведущий комнаты закрывает вкладку браузера или теряет связь на этапе ожидания в лобби (`phase === 'LOBBY'`).
* **Возможные последствия:** Оставшиеся игроки не могут запустить партию и вынуждены покидать комнату.
* **Рекомендуемый способ исправления:**
  Если в фазе `LOBBY` хост находится в статусе `connected === false` более 30–45 секунд, автоматически передавать статус `isHost: true` первому подключенному игроку и рассылать `broadcastState()`.
* **Необходимые проверки после исправления:** Создать комнату 2 игроками, закрыть вкладку хоста, проверить передачу прав хоста второму игроку через таймаут.

* **Уровень критичности:** **P2 (Средний / Архитектурный риск)**
* **Подсистема:** Каталог предметов / Медиа-ресурсы лутбоксов
* **Статус:** Подтверждено (В соответствии с инструкцией: миграцию не выполнять, зафиксировать рекомендации)
* **Конкретные файлы и функции:**
  * Файлы: `server/db/items.ts` (`saveMediaAsset`), `server.ts` (`GET /api/lootboxes/runtime-resources`, строки 2329–2350)
* **Техническое доказательство проблемы:**
  При загрузке аудиофайлов для лутбоксов через административный конструктор файл преобразуется в Data URL (`data:audio/mp3;base64,...`) и записывается прямо в колонку `source_url` таблицы `lootbox_media_assets`.
  При вызове публичного эндпоинта `/api/lootboxes/runtime-resources` метод `itemsDb.getMediaAssets()` считывает и отдает клиенту полные base64-строки всех медиафайлов сразу, даже если клиенту нужны только метаданные и URL.

* **Рекомендуемый способ исправления (на будущее):**
  1. В `runtime-resources` отдавать медиа-ресурсы без `source_url`, заменяя его на URL потокового эндпоинта `/api/lootboxes/media/:assetId`, который уже реализован и кэширует отдачу с заголовком `Cache-Control: immutable`.
  2. В перспективе перенести бинарные файлы звуков в объектное хранилище (Cloudflare R2 / AWS S3 / Google Cloud Storage), сохранив в базе только внешние HTTP URL.

### 7. `WEBRTC-01`: Высокая нагрузка P2P Mesh-топологии на мобильные устройства при 10 игроках
* **Уровень критичности:** **P3 (Низкий / Архитектурное ограничение)**
* **Подсистема:** Видеосвязь WebRTC
* **Статус:** Подтверждено
* **Конкретные файлы и функции:**
  * Файлы: `src/hooks/useWebRtc.ts`, `server.ts` (сигналинг WebSockets)
* **Техническое доказательство проблемы:**
  Платформа использует полносвязную P2P Mesh топологию ($N \times (N-1)$ соединений). При 10 игроках с включёнными камерами каждый телефон должен одновременно кодировать и передавать 9 исходящих видеопотоков и декодировать 9 входящих видеопотоков.
* **Условия возникновения:** Матч классической мафии на 10 участников с одновременным включением видеокамер.
* **Возможные последствия:** Троттлинг процессора на мобильных устройствах, быстрый разряд аккумулятора, задержки звука при слабом мобильном интернете 4G.
* **Рекомендуемый способ исправления:**
  1. Добавить в настройки лобби тумблер качества видео (Low/Medium/High) и ограничение разрешения (320x240 @ 15fps для сетки стола).
  2. Передавать видеопоток высокой четкости только для текущего говорящего игрока (`currentSpeakerId`), а для остальных участников стола передавать миниатюры или только аудио.
  3. В будущем для масштабирования рассмотреть внедрение SFU-сервера (LiveKit или Mediasoup).

## 🚀 ЭТАП 4. ПЛАН ДАЛЬНЕЙШЕГО РАЗВИТИЯ

### 1. Что обязательно выполнить до публичного запуска (Блокирующие задачи)
1. **Подключение Turso Cloud (`INFRA-01`):** Создать production-базу в Turso, настроить переменные `TURSO_DATABASE_URL` и `TURSO_AUTH_TOKEN` на Render. Проверить миграции всех 35 таблиц.
2. **Настройка почтового транспорта Resend (`server/utils/mailer.ts`):** Прописать рабочий `RESEND_API_KEY` в окружении Render и отправить тестовое письмо через `/api/admin/mail/test`, чтобы убедиться в доставке кодов сброса пароля и верификации email.
3. **Исправление сохранения скинов интерфейса (`COSM-01`):** Добавить колонку `equipped_ui_skin` в таблицу `users`, чтобы купленные на Черном Рынке скины не слетали при перезагрузке.
4. **Защита от дублей наград в тикетах (`ECON-01`):** Заблокировать повторное начисление кредитов при повторном сохранении резолюции тикета в панели администратора.
5. **Сборщик мусора комнат (`PERF-01`):** Добавить 60-секундный таймер уничтожения заброшенных пустых комнат, оставшихся без игроков более 15 минут.

### 2. Что необходимо проверить с несколькими реальными игроками
1. **Полный матч Городской мафии (6–8 игроков):** Проверить последовательность фаз: день -> речи -> выдвижение -> суд -> переголосование -> ночь (действия доктора, куртизанки, шерифа, мафии) -> утро -> объявление победы и начисление наград в истории.
2. **WebRTC аудио/видео сетка:** Проверить включение микрофонов и камер у 4–6 участников с мобильных устройств (iOS Safari, Android Chrome) для оценки задержек и стабильности звука.
3. **Реконнект во время активной игры:** Игрок закрывает вкладку во время дневного обсуждения и входит повторно по коду комнаты через 20 секунд — проверить, что он садится на свое место с сохранением роли и карты.
4. **Активация партнерского промокода при регистрации:** Зарегистрировать нового игрока с кодом партнера, проверить появление связки в `user_partner_bindings` и моментальное начисление наград игроку.
5. **Стартовая акция открытия платформы:** Проверить вход игрока во время активной акции открытия — убедиться в появлении модального окна чествования подарка и корректном начислении кредитов и предметов в инвентарь.

### 3. Что желательно улучшить после запуска (Первые недели работы)
1. **Ленивая загрузка админки (`React.lazy` для `AdminPanelModal`):** Уменьшить размер стартового JS-бандла для игроков на 25%.
2. **Автоматическая смена ведущего в лобби (`GAME-02`):** Передавать права хоста второму игроку через 30 секунд после отключения создателя стола.
3. **Урезанная роль модератора (`SEC-01`):** Выделить отдельный ограниченный интерфейс для модераторов (только мониторинг столов, чатов и жалоб без доступа к экономике и почтовым рассылкам).
4. **Улучшение мобильного видеопотока:** Ограничить частоту кадров миниатюр стола до 15 fps для снижения энергопотребления смартфонов.

### 4. Какие архитектурные изменения целесообразны в будущем
1. **Вынос Base64 аудиофайлов в Object Storage (S3 / Cloudflare R2):** Полностью разгрузить базу Turso от бинарных ассетов лутбоксов, переведя их на статический CDN.
2. **Внедрение WebRTC SFU (Selective Forwarding Unit):** При росте онлайна до десятков одновременных комнат перейти с P2P Mesh на выделенный SFU-сервер (LiveKit/Mediasoup), чтобы каждый игрок отправлял только один исходящий поток.
3. **Рейтинговый сезонный матчмейкинг:** Автоматический подбор столов по рейтингу Elo с защитой от сговора друзей в рейтинговых матчах.

### 5. Какие уже реализованные системы не требуют дополнительных работ
* **Система обычных промокодов (`promo_codes`):** Полностью готова, поддерживает бессрочные и временные циклы, лимиты, снимки наград и многоуровневую защиту от накруток.
* **Реферальная партнерская программа (`partners`):** Полностью готова, содержит анти-фрод от саморефералов, квалификационные требования и независимую обработку выплат без взаимных блокировок.
* **Единый часовой пояс проекта (`timezone`):** Полностью отлажен, сохраняет даты в UTC ISO, независим от смены часового пояса сервера или браузера.
* **Подарочные акции платформы («Акции»):** Полностью реализованы со 100% прохождением 17 автоматических тестов, 3-секундным свипером онлайна и сохранением прав при дисконнекте.
* **Единый каталог предметов и снимки инвентаря:** Полностью защищают экономику от порчи предметов при редактировании магазина.
* **Криптографическая верификация Google Auth и сброс паролей:** Полностью защищены bcrypt-хешированием и проверкой сертификатов Google.
