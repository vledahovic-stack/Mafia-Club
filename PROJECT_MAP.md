## 1. ОБЩАЯ АРХИТЕКТУРА И ТЕХНОЛОГИЧЕСКИЙ СТЕК

### 1.1. Назначение проекта
**Mafia Club («Мафия Онлайн: Город Засыпает»)** — кроссплатформенная многопользовательская веб-платформа реального времени для игры в классическую (спортивную) и городскую Мафию. Платформа включает полнофункциональный игровой движок, WebRTC-видеосвязь между участниками стола, развитую мета-систему (уровни, динамический опыт XP, мастерство ролей, кланы, кастомизация, магазин, ломбард, лутбоксы), единый настраиваемый часовой пояс, комплексную систему лояльности (приветственные награды, промокоды, реферальная программа, временные подарочные акции) и развитую панель администрирования из 16 разделов.

### 1.2. Технологический стек
* **Клиентская часть (Frontend):**
  * **React 19.0** + **TypeScript 7.0** + **Vite 8.3**
  * **Tailwind CSS v4** (кастомная noir/mafia палитра, адаптивная верстка под десктоп и мобильные устройства)
  * **Lucide React** (иконочный набор интерфейса)
  * **Recharts** (визуализация детальной статистики побед, ролей и выживаемости)
  * **Motion** (анимации переходов фаз матча, карточек и модальных окон)
  * **Canvas Confetti** (эффекты чествования побед и открытия подарков)
  * **Web Audio API** (`src/utils/audio.ts`) — синтезатор звуков и аудио-эффекты (выстрелы, колокол, таймер, победные фанфары)
  * **WebRTC P2P Mesh** (`src/hooks/useWebRtc.ts`) — передача видео и аудио потоков между игроками
  * **PWA & TWA** (`vite-plugin-pwa`, `twa-manifest.json`, `manifest.webmanifest`) — поддержка установки как PWA и Android Trusted Web Activity
* **Серверная часть (Backend):**
  * **Node.js** + **TypeScript** (`tsx server.ts`)
  * **Express 4.21** — организация REST API
  * **WebSockets (`ws` 8.22)** — real-time обмен игровыми состояниями, чатами, WebRTC-сигналингом и системными событиями
  * **@libsql/client 0.18** — универсальный драйвер реляционной базы данных (поддержка облачной СУБД Turso через HTTPS/WSS и локального SQLite файла `database.sqlite`)
  * **Bcryptjs 3.0** — криптографическое хеширование паролей пользователей, кодов верификации email и кодов сброса пароля
  * **Nodemailer 10.2** + **Resend REST API (HTTPS)** — двухрежимная почтовая подсистема доставки транзакционных писем
  * **Dotenv** — управление переменными конфигурации окружения
* **Архитектура процесса (Единый процесс):**
  * Сервер запускается на порту `3000`. В режиме разработки Express монтирует `vite.middlewares` для единого происхождения (Origin) фронтенда и API, устраняя проблемы CORS и кросс-доменных куки.
  * В production Express обслуживает скомпилированные статические файлы из `dist/` и обрабатывает маршруты SPA с fallback на `index.html`.

### 1.3. Точки входа приложения
* **Frontend:** `/index.html` -> `/src/main.tsx` -> `/src/App.tsx`.
* **Backend:** `/server.ts` (запуск HTTP/WebSocket сервера, инициализация базы данных LibSQL, запуск фоновых задач).

### 1.4. Фоновые задачи, таймеры и планировщики
1. **Игровой цикл комнат (`Room.startHeartbeatTimer` в `server/game/roomManager.ts`):** 
   * Интервал: 1000 мс (1 сек) для каждого активного экземпляра `Room`.
   * Назначение: декремент `phaseTimeRemaining`, автоматический переход игровых фаз (`advancePhase()`), отправка состояния игрокам через WebSocket.
2. **Свипер подарочных акций (`evaluateOnlineUsersForActiveCampaigns` в `server.ts`):** 
   * Интервал: 3000 мс (3 сек).
   * Назначение: опрос подключенных через WebSocket и активных пользователей, проверка действующих акций из таблицы `campaigns`, атомарное начисление подарков и отправка события `CAMPAIGN_GIFT_GRANTED`.
3. **Клиентский опрос акций (`checkCampaigns` в `src/App.tsx`):**
   * Интервал: 15 000 мс (15 сек).
   * Назначение: резервный HTTP-heartbeat через `/api/campaigns/check` для подтверждения присутствия в игре и получения непоказанных подарков.
4. **Клиентский опрос открытых комнат (`fetchPublicRooms` в `src/App.tsx`):**
   * Интервал: 5000 мс (5 сек) при нахождении в главном меню.
5. **Клиентский опрос друзей (`fetchFriends` в `src/components/FriendsView.tsx`):**
   * Интервал: 6000 мс (6 сек).

### 1.5. Внешние интеграции и конфигурация
* **Turso / LibSQL Cloud:** задается через `TURSO_DATABASE_URL` и `TURSO_AUTH_TOKEN`. При их отсутствии используется локальный `file:database.sqlite`.
* **Resend API / SMTP:** поддержка отправки через официальный HTTPS REST API Resend (`RESEND_API_KEY`) или классический SMTP (`SMTP_HOST`, `SMTP_PORT`, `SMTP_USER`, `SMTP_PASS`).
* **Firebase Auth (Google Sign-In):** клиентская инициализация в `src/firebase.ts` и валидация Firebase ID Token на сервере через публичные сертификаты Google X.509 (`server.ts`).

## 3. ИГРОВЫЕ МЕХАНИКИ И ДВИЖОК МАТЧЕЙ

### 3.1. Режимы игры
1. **Спортивная (Классическая) «Мафия» (`gameMode: 'sport'`):**
   * Строгий соревновательный формат.
   * Ровно 10 игроков (1 Дон, 2 Мафии, 1 Шериф, 6 Мирных жителей).
   * Ночная нулевая минута (`MAFIA_MEETING`, 60 сек) — знакомство преступного синдиката.
   * Фазы индивидуальных речей (`INDIVIDUAL_SPEECHES` по 60 сек на игрока по номерам стола).
   * Выдвижение кандидатов на голосование только во время своей речи (`currentSpeakerHasNominated`).
   * Голосование с переголосованием при ничьей (`REVOTE`), речью в защиту (`DEFENSE_SPEECH`) и последним словом (`LAST_WORDS_ARREST`).
2. **Городская «Мафия» (`gameMode: 'custom'`):**
   * Гибкий формат от 4 до 12+ участников с настраиваемым набором ролей.
   * Фаза общей свободной дискуссии (`DAY_DISCUSSION`).
   * Расширенный пул ролей (Доктор, Красотка/Куртизанка, Маньяк, Телохранитель).
   * Свободное голосование за любого подозреваемого.

### 3.2. Роли и их способности
| Идентификатор | Название | Команда | Способность |
| :--- | :--- | :--- | :--- |
| `civilian` | Мирный житель | Мирные | Дневное обсуждение и голосование |
| `mafia` | Мафия | Мафия | Совместный ночной выстрел |
| `don` | Дон Мафии | Мафия | Ночной выстрел (вес голоса 1.5) + ночной поиск Шерифа |
| `sheriff` | Шериф | Мирные | Ночная проверка игроков на принадлежность к Мафии |
| `doctor` | Доктор | Мирные | Ночное исцеление (спасение от гибели мафии или маньяка) |
| `courtesan` | Красотка / Куртизанка | Мирные | Ночной блок (заблокированная роль не может действовать ночью) |
| `maniac` | Маньяк | Одиночка | Ночное убийство любого игрока; цель — остаться одному |

### 3.4. Условия победы (`MafiaEngine.checkWinner`)
* **Победа Мирных жителей (`civilians`):** в живых не осталось ни одного представителя Мафии (Мафия, Дон) и Маньяка.
* **Победа Мафии (`mafia`):** количество живых членов Мафии равно или превышает суммарное количество всех остальных живых игроков (Мирные + Маньяк), и Маньяк мёртв.
* **Победа Маньяка (`maniac`):** Маньяк остался один либо 1 на 1 с мирным жителем при отсутствии мафии.

### 3.5. Переподключение и устойчивость связи
* При дисконнекте WebSocket соединение помечается как `player.connected = false`, рассылается WebRTC-уведомление `SIGNAL_PEER_LEFT`, комната продолжает функционировать без вылета игрока.
* При повторном входе через `JOIN_ROOM` сокет восстанавливается, статус переходит в `player.connected = true`, игрок получает полный снимок состояния `ROOM_STATE` и историю чата.

## 4. ПОЛЬЗОВАТЕЛИ, АВТОРИЗАЦИЯ И БЕЗОПАСНОСТЬ

### 4.1. Регистрация и аутентификация
* **Регистрация по Email/Паролю (`POST /api/auth/register`):**
  * Валидация формата email, минимальной длины пароля (6 символов).
  * Криптографическое хеширование пароля через `bcryptjs` (10 раундов соли).
  * Генерация высокоэнтропийного токена сессии `tk_<randomBytes(32)>`.
  * При регистрации проверяется и применяется реферальный код партнёра (с защитой от самореферала).
  * Автоматически оцениваются и начисляются приветственный бонус лояльности и действующие подарочные акции.
* **Авторизация по Email/Паролю (`POST /api/auth/login`):**
  * Сверка пароля через `bcrypt.compare`.
  * Ротация токена сессии.
  * Оценка подарочных акций и возвращение непоказанных наград.
* **Google Sign-In (`POST /api/auth/sync-google`):**
  * Строгая серверная проверка подлинности Firebase ID Token (`verifyFirebaseIdToken`) через открытые X.509 сертификаты Google.
  * Проверка `email_verified: true`.
  * Безопасное связывание или создание профиля без возможности подделки чужого email.

### 4.2. Верификация Email и сброс пароля
* **Верификация Email (`POST /api/auth/send-verification-code`, `/api/auth/verify-email`):**
  * Генерация 6-значного числового кода, сохранение его bcrypt-хеша в таблице `email_verification_codes`.
  * Срок действия: 15 минут, счётчик попыток: максимум 5.
  * При подтверждении email статус учетной записи обновляется (`is_email_verified = 1`), начисляется бонус лояльности за подтверждение почты.
* **Восстановление пароля (`POST /api/auth/forgot-password`, `/api/auth/reset-password`):**
  * Защита от перебора: распределённый rate limiting по IP (`ip_rate_limits`, 5 запросов за 15 минут).
  * Отправка 6-значного кода через настроенный транспорт почты (Resend HTTPS API / SMTP).
  * Код хранится исключительно в виде bcrypt-хеша.
  * При успешном сбросе старый код удаляется, а в `audit_logs` фиксируется запись безопасности.

### 4.3. Сессии и права доступа
* **Сессионный токен:** передается клиентом в заголовке `Authorization: Bearer <token>` или в query-параметре `?token=`.
* **Бан пользователя:** при установке `is_banned = 1` сессионный токен немедленно обнуляется (`session_token = null`), что приводит к мгновенному отключению всех активных сессий пользователя на сервере.
* **Проверка прав администратора (`requireAdmin` в `server.ts`):**
  * Проверяется наличие сессии.
  * Проверяется совпадение email с `ADMIN_EMAIL` (по умолчанию `vledahovic@gmail.com`), вхождение в `ADMIN_EMAILS`, либо флаги `user.isAdmin === true` / `user.role === 'admin'`.

## 5. ЭКОНОМИКА, ЕДИНЫЙ КАТАЛОГ И ИНВЕНТАРЬ

### 5.1. Единый каталог предметов (`server/db/items.ts`, `src/data/items.ts`)
Все предметы платформы унифицированы в едином каталоге со строгими правилами:
* **Категории:**
  * `certificates`: Сертификат смены никнейма (`cert_name_change`), Сертификат смены аватара (`cert_avatar_change`).
  * `chests`: Лутбоксы и сундуки (`chest_novice`, `chest_don`, кастомные лутбоксы).
  * `cosmetics`: Рубашки карт (`card_back_noir`, `card_back_gold`), титулы, скины интерфейса.
  * `valuables`: Карточка выбора роли (`card_role_select`), валюта (`currency_credits`).
* **Редкости (`RARITY_CONFIG`):** `common` (Обычный), `rare` (Редкий), `epic` (Эпический), `legendary` (Легендарный).
* **Снимки (Snapshot isolation):** при выдаче предмета в инвентарь игрока записывается неизменяемый снимок параметров (`nameSnapshot`, `iconSnapshot`, `pawnValueSnapshot`, `ruleSnapshot` для лутбоксов). Даже при удалении предмета администратором из магазина предмет в инвентаре игрока сохраняет работоспособность или может быть сдан в ломбард по правилам `deleted_item_replacements`.

### 5.2. Валюта и транзакции
* **Кредиты (`credits`):** целочисленный баланс профиля игрока.
* **Транзакционный журнал (`economy_transactions`):**
  * Запись всех операций начисления/списания с уникальным ключом идемпотентности `idempotency_key`.
  * Поля: `user_id`, `operation_type`, `source_type`, `source_id`, `credits_delta`, `items_json`, `metadata_json`.
* **Защита от отрицательного баланса:** на уровне SQL-запросов выполняется условие `WHERE id = ? AND credits >= ?`.

### 5.3. Магазин и Ломбард
* **Покупка предметов (`POST /api/user/buy-item`):**
  * Блокировка мьютекса `rewardMutex.runExclusive('user:' + userId)`.
  * Проверка доступности товара в магазине (`inShop === true`, `isAvailable === 1`).
  * Учёт глобальной скидки магазина (`globalDiscount`).
  * Атомарное списание кредитов и добавление предмета в инвентарь в рамках LibSQL `write` транзакции.
* **Ломбард (`POST /api/user/pawn-item`):**
  * Выкуп ненужных предметов у игроков за фиксированную стоимость (`pawnValue`).
  * Поиск конкретного экземпляра предмета по `inventoryEntryId`.
  * Атомарное удаление предмета из инвентаря и начисление кредитов.

### 5.4. Механизм Лутбоксов
* **Открытие лутбокса (`POST /api/user/use-item`):**
  * Поддержка двух режимов выпадения (`dropMode`):
    1. `single_weighted` — выбор ровно одной награды по весовым коэффициентам.
    2. `independent` — независимый расчет вероятности для каждого предмета с утешительным призом (`consolationPrize`) при нулевом выпадении.
  * **Идемпотентность (`lootbox_open_operations`):** клиент передает уникальный `operationId`. При повторном запросе сервер возвращает сохранённый результат без повторного списания сундука.
  * Возможность вложенных лутбоксов (`allowNestedLootboxes`).

## 6. ПРОГРАММА ЛОЯЛЬНОСТИ, ПРОМОКОДЫ И АКЦИИ

### 6.1. Бонусы лояльности (`server/db/loyalty.ts`)
* **Приветственный бонус (`bonusType: 'registration'`):** автоматическое начисление настроенных наград (кредиты + предметы) сразу после создания аккаунта.
* **Бонус за подтверждение email (`bonusType: 'email_verification'`):** выдается один раз при успешном вводе проверочного кода.
* Реестр начислений ведется в таблице `loyalty_bonus_claims` с ограничением `UNIQUE(user_id, bonus_type)`.

### 6.2. Ежедневный бонус (`server/db/dailyBonus.ts`)
* 7-дневная прогрессивная сетка наград с поддержкой серий (стриков).
* Гибкая политика заходов (`streak_policy: 'flexible_24h'`) с кулдауном 20 часов.
* Защита от повторного сбора через учет даты в едином часовом поясе проекта (`last_daily_bonus_claim_date_tz`).

### 6.3. Обычные промокоды (`promo_codes` в `server/db/promocodes.ts`)
* Поддержка двух типов расписания:
  * `indefinite`: бессрочный.
  * `custom_dates`: строгий период действия с конвертацией локального времени проекта в UTC ISO.
* Типы лимитов активаций:
  * `unlimited`: без ограничений по количеству игроков.
  * `total_limit`: глобальный лимит на N первых игроков.
* Защита: ровно 1 активация на игрока в рамках текущего цикла (`cycle_key`), блокировка параллельных гонок через глобальный мьютекс `promo_global_activation` и персональный мьютекс пользователя.

### 6.4. Партнерская реферальная программа (`partners`, `partner_referral_codes`)
* Назначение партнёров администратором с генерацией уникального реферального кода.
* **Однократная пожизненная привязка:** игрок связывается с партнёром один раз (`user_partner_bindings`), повторный ввод других реферальных кодов заблокирован.
* **Анти-фрод:**
  * Запрет саморефералов (партнёр не может активировать собственный код).
  * Защита от создания фейковых аккаунтов: начисление награды партнёру может требовать квалификации игрока (сыграть N матчей, провести N минут в игре, достичь уровня L).
  * Раздельная обработка выплат партнёру без взаимной блокировки (Deadlock-Free).

### 6.5. Подарочные акции («Акции», `server/db/campaigns.ts`)
* Автоматическая выдача подарков игрокам во время открытия платформы, праздников и событий:
  * Находящимся в игре онлайн (через 3-секундный фоновый свипер и WebSocket `CAMPAIGN_GIFT_GRANTED`).
  * Входящим в игру в период действия акции.
  * Регистрирующимся во время проведения акции.
* **Гарантия сохранения прав:** если пользователь был в сети во время акции, но отключился до фиксации, создается запись со статусом `entitled_pending`. Подарок гарантированно выдается при следующем входе даже после окончания акции.
* **Ненавязчивость в матчах:** модальное окно подарка откладывается, если игрок участвует в игре (`phase !== 'LOBBY' && phase !== 'GAME_OVER'`), и показывается в лобби или на экране победы.
* Строгая уникальность `UNIQUE(campaign_id, user_id)` в таблице `campaign_claims`.

39. `partner_referral_codes` — реферальные промокоды партнеров и настройки наград.
40. `user_partner_bindings` — фиксация привязки игрока к партнеру.
41. `promo_activations` — журнал активаций промокодов со снимками прогресса игрока.
42. `promo_reward_obligations` — отложенные обязательства наград игроку и партнеру.
43. `user_daily_activity` — календарная активность игроков в часовом поясе проекта.
44. `project_settings` — глобальные системные настройки (включая `timezone`).
45. `campaigns` — подарочные акции платформы с расписанием.
46. `campaign_claims` — журнал начислений подарков акций (`UNIQUE(campaign_id, user_id)`).

### 8.2. Транзакции и блокировки
* **LibSQL Транзакции:** критические финансовые операции (покупка, сдача в ломбард, открытие лутбокса, сбор квеста, начисление промокода) выполняются внутри явных транзакций `db.transaction('write')`.
* **Серверный мьютекс (`rewardMutex` в `server/utils/asyncLock.ts`):** строгая сериализация параллельных асинхронных операций над одним пользователем (`user:${userId}`). Исключает race conditions при одновременных кликах или параллельных сетевых запросах.

### 8.3. Единый часовой пояс проекта (`project_settings.timezone`)
* Централизованно настраивается администратором через интерфейс настроек проекта (по умолчанию `Europe/Moscow`, поддерживаются все стандартные зоны IANA).
* Все даты в базе данных хранятся строго в формате **UTC ISO 8601** (`YYYY-MM-DDTHH:mm:ss.sssZ`).
* При вводе в админке даты расписания промокодов и акций конвертируются из локального времени проекта в абсолютное время UTC. Последующее изменение пояса проекта не смещает фактический момент проведения уже сохраненных акций.
* Календарные дни для дейли-бонусов и активности партнёров рассчитываются строго в часовом поясе проекта.

### 8.4. Особенности развертывания на Render
* **Эфемерная файловая система:** на тарифе Render Free файловая система контейнера сбрасывается при каждом перезапуске или обновлении сервиса.
* **Требование к Turso:** для обеспечения сохранности данных игроков, инвентаря и матчей в production **критически необходимо** указать переменные окружения `TURSO_DATABASE_URL` и `TURSO_AUTH_TOKEN`.
* **Порты почты:** исходящие порты SMTP (25, 465, 587) на Render Free блокируются на уровне хостинга. Решением является переключение транспорта на **Resend REST API (HTTPS порт 443)**, полностью реализованное в модуле `server/utils/mailer.ts`.
