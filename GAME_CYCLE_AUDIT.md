# Комплексный технический и логический аудит полного игрового цикла Mafia Club

---

## 1. Архитектурная карта игрового процесса

Игровой процесс Mafia Club построен на гибридной модели: создание комнат и первичный листинг осуществляются через HTTP REST API, а всё управление лобби, жизненным циклом матча, фазами, таймерами, голосованием, ночными действиями и WebRTC-сигналингом — через двусторонний WebSocket-канал с центральным авторитетным игровым сервером (`Room` / `RoomManager`).

```
┌────────────────────────────────────────────────────────────────────────┐
│                              КЛИЕНТ (React)                            │
│  HomeView ──(HTTP POST /api/rooms)──> App.tsx (handleCreateRoom)       │
│                                                │                       │
│  LobbyView / InGameView <───(WS /ws)───────────┴── App.tsx (WS Client) │
└─────────────────────────────────┬──────────────────────────────────────┘
                                  │ JSON WebSocket Messages
                                  ▼
┌────────────────────────────────────────────────────────────────────────┐
│                             СЕРВЕР (Node.js)                           │
│  server.ts                                                             │
│   ├── REST: POST /api/rooms, GET /api/rooms, GET /api/lobby/:code      │
│   └── WS Handler (/ws):                                                │
│         INIT_USER, JOIN_ROOM, LEAVE_ROOM, START_GAME, RESTART_GAME,    │
│         NOMINATE_PLAYER, CAST_VOTE, SUBMIT_NIGHT_ACTION, SKIP_PHASE... │
│         └── RoomManager.getRoom(code) ──> Room Instance                │
└─────────────────────────────────┬──────────────────────────────────────┘
                                  │
                                  ▼
┌────────────────────────────────────────────────────────────────────────┐
│                    ДВИЖОК И СОСТОЯНИЕ (In-Memory + DB)                 │
│  server/game/roomManager.ts (Класс Room, цикл setInterval 1 сек)       │
│   ├── advancePhase() ──> Фазовый конечный автомат                      │
│   ├── getClientState(userId) ──> Маскирование ролей и тумана войны     │
│   └── MafiaEngine (server/game/engine.ts)                              │
│         ├── distributeRoles() ──> Раздача ролей с учетом карточек      │
│         ├── resolveNight()    ──> Обработка выстрелов, проверок, хила  │
│         └── checkWinner()     ──> Проверка победы после фаз            │
│   └── recordGameResult (server/db/users.ts) ──> Транзакция SQLite/DB   │
└────────────────────────────────────────────────────────────────────────┘
```

### Ключевые файлы и их зоны ответственности:
1. **Клиентская часть:**
   - `src/App.tsx`: Корневой координатор. Управляет подключением к WS (`wsRef`), маршрутизацией экранов (`view: 'home' | 'room'`), локальным состоянием комнаты (`roomState`), модальными окнами (`MorningReportModal`, `GameOverModal`).
   - `src/components/HomeView.tsx`: Список активных столов, фильтры, запуск модального окна создания комнаты.
   - `src/components/CreateRoomModal.tsx`: Конфигурация параметров создаваемой комнаты (режим, количество игроков, таймеры, приватность).
   - `src/components/LobbyView.tsx`: Экран ожидания. Сетка игроков/ботов, выбор карточек роли, кнопка старта для хоста, переключение в зрители.
   - `src/components/InGameView.tsx`: Основной игровой стол. Рендеринг видеослотов, фазовых плашек, центральной консоли речей, списков голосования, ночных действий и чата.
   - `src/components/MorningReportModal.tsx`: Утренний отчет о ночных событиях (убитые, заблокированные, спасенные).
   - `src/components/GameOverModal.tsx`: Экран завершения матча. Победившая команда, детальная таблица ролей, начисление XP/кредитов/рейтинга, кнопка «Сыграть снова».
   - `src/types/mafia.ts`: Единый реестр типов TypeScript (фазы, роли, типы действий и сетевых сообщений).

2. **Серверная часть:**
   - `server.ts`: Маршруты Express REST (`/api/rooms`) и диспетчер входящих WS-событий (`ws.on('message')`). Перенаправляет вызовы в `roomManager`.
   - `server/game/roomManager.ts`: Жизненный цикл комнаты (экземпляр класса `Room`). Авторитетный секундный таймер (`setInterval`), фазовые переходы (`advancePhase`), валидация голосов и действий, генерация клиентских проекций (`getClientState`) и вещание (`broadcastState`).
   - `server/game/engine.ts`: Чистый игровой движок (`MafiaEngine`). Пул ролей, распределение ролей с учетом инвентаря, расчет результатов ночи (выстрелы мафии/маньяка, лечение доктора, проверка шерифа/дона, блокировка путаны), правила победы (`checkWinner`).
   - `server/db/users.ts`: Метод `recordGameResult`. Расчет наград (XP, рейтинг, авторитет, победы/поражения) с использованием мьютекса, запись в таблицу `match_history` и обновление статистики пользователей.

## 2. Инвентаризация реально существующих режимов игры

В системе объявлено два игровых режима (`GameMode`):

| Параметр / Механика | Классический режим (`classic`) | Спортивный / Турнирный режим (`sport`) |
| :--- | :--- | :--- |
| **Количество игроков** | 4 – 16 игроков | Строго 10 игроков (в UI селектор фиксирует 10) |
| **Пул доступных ролей** | Мафия, Дон, Шериф, Доктор, Путана, Маньяк, Мирные жители | Строго: 1 Дон, 2 Мафии, 1 Шериф, 7 Мирных жителей (всего 10) |
| **Ночные спец-роли** | Доктор (лечение), Путана (блок), Маньяк (соло-выстрел) активны | Доктор, Путана, Маньяк отсутствуют; активны только Дон и Шериф |
| **Фаза Дня: Индивидуальные речи** | Присутствует (по очереди с таймером `speechTime`) | Присутствует (строго по 60 секунд на игрока) |
| **Фаза Дня: Общее обсуждение** | Присутствует (`dayDiscussionTime`, если включено в настройках) | Отсутствует (только индивидуальные речи и перестрелка) |
| **Механика номинаций** | Любой живой игрок может выставить кандидатов | Только говорящий игрок на своей речи выставляет кандидатов |
| **Голосование и Ничья** | Дневное голосование. При ничьей — перестрелка (защитные речи), затем повторное голосование. При повторной ничьей: если включено `killOnTie` — умирают все лидеры, иначе — никто не выбывает | Классическая перестрелка по 30 сек. При повторной ничьей — голосование «кто за то, чтобы все покинули стол» (в текущем коде упрощено до ненасильственного исхода) |
| **Прощальные слова** | Есть (`lastWordsArrestTime`, `lastWordsKilledTime`) | Есть (1 минута на прощальную речь) |

## 5. Аудит создания комнаты

1. **Генерация кода комнаты:**
   - Выполняется в `roomManager.ts:1829`: `Math.random().toString(36).substring(2, 8).toUpperCase()`. Код 6-значный (буквы + цифры).
   - **Уязвимость:** Метод `roomManager.createRoom` не выполняет проверку коллизий в цикле `while (this.rooms.has(code))`. При совпадении кода существующая комната будет перезаписана в словаре `this.rooms`.
2. **Валидация параметров комнаты (`POST /api/rooms`):**
   - Проверяется имя (`name`), режим (`mode`), лимиты игроков (`maxPlayers` от 4 до 16).
   - Если передан некорректный payload, возвращается `400 Bad Request`.
   - **Дефект на клиенте (`App.tsx:671–688`):** При получении статуса 400 или 500 вызов `fetch` не генерирует исключение. `res.ok === false`, но ветка `catch` не срабатывает. Ошибка пользователю не выводится, модальное окно просто закрывается без перехода.
3. **Синхронизация в БД:**
   - Комната сохраняется в SQLite-таблицу `game_rooms`. При создании выполняется `INSERT OR REPLACE INTO game_rooms`.

## 6. Аудит лобби и механики старта

1. **Роли и карточки ролей:**
   - Карточки ролей (`role_card_*`) передаются через `SELECT_ROLE`. При старте партии метод `engine.ts:distributeRoles` учитывает приоритеты игроков, гарантируя применение купленных карт и списывая их с баланса (`consumePlayerItem`).
2. **Готовность и запуск:**
   - Право запуска принадлежит исключительно хосту (`room.hostId === userId`).
   - Проверяется минимальное число игроков: `>= 4` (в режиме `sport` — строго 10).
3. **Блокировка кнопки старта (`isStartingGame`):**
   - **Обнаружен критический UX-баг в `LobbyView.tsx:147, 807–817`:** При нажатии «Раздать карты» устанавливается локальный флаг `setIsStartingGame(true)`. Если сервер отклонил старт (например, игрок только что отключился и осталось 3 участника), сервер шлет `ERROR: "Нужно минимум 4 игрока"`. Но на клиенте `isStartingGame` **никогда не сбрасывается обратно в `false`**, так как нет тайм-аута или `useEffect` по `roomState.phase`. Кнопка блокируется навсегда до полной перезагрузки страницы хостом.

## 7. Аудит игровых фаз, таймеров и действий ролей

1. **Фазовый автомат (`roomManager.ts:advancePhase`):**
   - Переходы фаз синхронизированы центральным таймером комнаты `setInterval` с частотой 1000 мс.
   - Сервер инкрементирует `phaseTimeElapsed` и проверяет условие `phaseTimeElapsed >= phaseDuration`.
2. **Индивидуальные речи (`INDIVIDUAL_SPEECHES`):**
   - Очередь речей формируется строго по номерам слотов живых игроков.
   - Завершение речи досрочно доступно говорящему игроку (`SKIP_PHASE`) или по истечении таймера.
3. **Голосование и Ничья (`VOTING` -> `DEFENSE_SPEECHES` -> `REVOTE`):**
   - Если один кандидат набрал большинство голосов — он исключается.
   - Если два или более кандидата набрали одинаковое максимальное число голосов, комната переходит в фазу `DEFENSE_SPEECHES` (защитные речи кандидатов), затем в `REVOTE`.
4. **Ночная фаза и действия ролей:**
   - Живые игроки с активными ролями отправляют выбор через `SUBMIT_NIGHT_ACTION`.
   - **Обнаружен дефект проверки Шерифа/Дона (`roomManager.ts:1619–1640`):** Результат проверки рассчитывается «на лету» прямо в методе `getClientState` до завершения ночи. Если Шериф кликнул на игрока, он мгновенно получает результат проверки в сокете. Если после этого Путана заблокирует Шерифа, утренний отчет напишет «Шериф был заблокирован», но игрок **уже увидел роль цели в клиенте**.
   - **Обнаружен дефект разделения выстрелов Мафии (`engine.ts:217–223`):** Если мафиози проголосовали в разных игроков (1 в одного, 1 в другого), побеждает тот, чье ID случайно оказалось первым при итерации ключей объекта `targetVoteCounts`. Это недетерминированное поведение вместо фиксации промаха при несогласованной стрельбе.
   - **Настройка `allowSelfHealOnce` (самолечение доктора):** Объявлена в типах и настройках комнаты, но в коде `engine.ts` и `roomManager.ts` отсутствует какая-либо проверка счетчика самолечения: Доктор может лечить себя каждую ночь без ограничений.

## 8. Аудит условий победы

Проверка победы выполняется централизованно в `engine.ts:checkWinner(state)`:
- **Победа Мафии (`mafia`):** Число живых мафиози `>=` числу живых мирных жителей (и маньяк мертв).
- **Победа Мирных (`civilians`):** Все мафиози и маньяк мертвы, и есть хотя бы 1 живой игрок.
- **Победа Маньяка (`maniac`):** Маньяк остался 1 на 1 с мирным или мафиози, либо остался единственным выжившим.
- **Граничный дефект:** Если ночью Маньяк и Мафия одновременно убивают друг друга и на столе не остается ни одного выжившего (0 живых), условие `aliveMafia.length === 0 && aliveManiac.length === 0` вычисляется как `true`, и победа присуждается мирным жителям, несмотря на то, что все мирные мертвы.

## 9. Аудит начисления результатов, опыта и истории матчей

1. **Транзакция завершения партии (`users.ts:recordGameResult`):**
   - Вызывается при переходе в `GAME_OVER`. Обернута в мьютекс семафора, что предотвращает параллельную перезапись баланса игрока.
   - Начисляет:
     - Опыт (XP) за победу / поражение / выживание / результативные действия ролей.
     - Игровые кредиты (монеты).
     - Рейтинг авторитета (`rating`).
2. **Запись в историю матчей (`match_history`):**
   - **Обнаружен дефект (`users.ts:2390`):** В SQL-запросе вставки записи матча значение `room_code` захардкожено как `null` (`VALUES (?, ?, ?, null, ...)`). Из-за этого в профиле игрока история матчей не отображает код комнаты, в которой проходила игра.

## 10. Аудит отключений, реконнектов и пограничных ситуаций

1. **Разрыв соединения (`ws.on('close')`):**
   - При дисконнекте флаг игрока меняется: `player.connected = false`. Игрок не удаляется из матча сразу, что позволяет ему переподключиться.
   - При повторном `JOIN_ROOM` сокет связывается с существующим слотом (`player.connected = true`).
2. **Проблема отключения хоста в лобби:**
   - Если хост закрывает вкладку в фазе `LOBBY`, статус хоста не передается автоматически следующему игроку (передача происходит только при явном вызове `LEAVE_ROOM`). В результате оставшиеся игроки не могут нажать «Старт», а слот хоста числится оффлайн.
3. **Утечка комнат и таймеров (Зомби-комнаты):**
   - Если все игроки покинули комнату или закрыли вкладки, таймер `setInterval` экземпляра `Room` продолжает работать бесконечно. Очистка `roomManager.removeRoom` вызывается только через закрытый эндпоинт админки.

## 12. Потенциальные риски, требующие дополнительной проверки

1. **Нагрузка WebRTC при 16 игроках:**
   - Модель P2P Mesh (каждый передает каждому) создает $N \times (N - 1)$ соединений (до 240 peer-соединений в комнате на 16 человек). Требует верификации стабильности сети и загрузки процессора клиента.
2. **Асинхронность и задержка сокетов при окончании таймера:**
   - Если клиент отправляет голос на последней секунде ($t=0.1$ с), сообщение может прийти на сервер, когда фаза уже сменилась на `DEFENSE_SPEECHES` или `NIGHT`. Голос будет проигнорирован.
3. **Рассинхронизация клиентского и серверного таймера:**
   - Клиент интерполирует время между пакетами `ROOM_STATE_UPDATE`. При лагах соединения таймер на клиенте может показывать 0, пока сервер не пришлет обновленное состояние.

## 14. Сценарии для тестирования

### Сценарий 1: Проверка нумерации дней
- **Шаги:** Запустить партию с ботами. Пройти День 1 -> Голосование -> Ночь 1 -> Утро.
- **Ожидаемый результат:** Наступивший день имеет номер **2** (а не 3). В ленте событий и плашке отображается «День 2».

### Сценарий 2: Выход игроков после матча
- **Шаги:** Довести партию до финала (`GAME_OVER`). Хост не нажимает «Сыграть снова». Обычный игрок нажимает кнопку выхода.
- **Ожидаемый результат:** Обычный игрок успешно возвращается на главный экран (`HomeView`), его статистика корректно сохранена.

### Сценарий 3: Сбой старта лобби
- **Шаги:** Создать комнату, добавить 3 ботов (всего 4). Отключить одного бота. Нажать «Раздать карты».
- **Ожидаемый результат:** Сервер присылает предупреждение о нехватке игроков. Кнопка «Раздать карты» снова становится активной, не блокируя интерфейс.

### Сценарий 4: Проверка Шерифа и блокировка Путаны
- **Шаги:** Шериф выбирает игрока №2. В ту же ночь Путана выбирает Шерифа.
- **Ожидаемый результат:** Шериф не получает роль игрока №2 ни во время ночи, ни утром. Утром выводится сообщение о блокировке Шерифа.
